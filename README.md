# EmberWatch

**One fire record for 25 years, with the sensor seams taken out.**

Built for the NASA Space Apps Challenge 2026 challenge
[Harmonization of MODIS and VIIRS Hot Spots](https://www.spaceappschallenge.org/2026/challenges/modis-and-viirs-hot-spots/).

Satellites have tracked active fire hotspots for over two decades, but the record is split
across sensors that cannot be compared directly. MODIS Collection 6.1 runs from 1 November
2000 at a nominal 1 km fire pixel; VIIRS runs from 20 January 2012 at 375 m and detects
smaller, cooler fires. Plot both and it looks like burning exploded in 2012. It did not.
The instrument changed.

EmberWatch harmonises the two into a single burning activity calendar for any area, so a
fire manager can see which months and years actually burned, and how the current month
compares with history.

## The result

Size of the artificial jump at the 2012 sensor change, same area, measured the same way:

| Variant | Step at the sensor change |
| --- | --- |
| Raw splice, no floor | +213% |
| Shared FRP floor | -42% |
| Floor plus per-cell calibration | **+12%** |

That table is generated by the pipeline, not written by hand. It is the project's own
self-check: if harmonisation works, the seam closes.

## Method

1. **One schema.** Both sensors collapse into a single table. MODIS reports confidence as
   0-100 and VIIRS as low/nominal/high, so MODIS is mapped onto the categorical scale.
2. **Grid and bin.** Detections go onto a 0.25 degree grid and monthly bins. Raw point
   counts are never compared across sensors, because pixel size drives them.
3. **Cell-days.** The unit of analysis is one grid cell on one day with any active burning.
   This is close to invariant under pixel size and under how many platforms are flying,
   which removes most of the inter-sensor bias before any calibration.
4. **Shared sensitivity floor.** Both sensors are clipped to the weakest fire MODIS
   reliably reports, taken from the 5th percentile of its own FRP distribution. Without
   this, VIIRS's extra sensitivity reads as a change in the world.
5. **Calibration on the overlap.** Per cell and per calendar month, the median ratio of
   VIIRS to MODIS cell-days across the overlap years, falling back to a month-wide then
   global ratio where a cell has too few years. Medians, because fire data is heavily
   right-skewed. Every value carries its factor, the fallback level and the sample size.
6. **Seam test.** The series is plotted across the join, raw and harmonised, and the step
   is measured. Evidence, not assertion.

### Statistics

- **Anomalies** are percentile ranks within the same calendar month's history, not
  z-scores: fire counts are strongly right-skewed and not normal.
- **The running month** is compared only against the same day-of-month window in previous
  years. Scoring 14 days of November against 25 complete Novembers would make every
  current month look quiet, which is how a monitoring tool becomes a dangerous one.
- **Trend** uses the seasonal Mann-Kendall test with a Theil-Sen slope, implemented in
  `pipeline/stats.py` rather than imported, so it can be audited. Each calendar month is
  its own season, so seasonality cannot masquerade as trend.

## Limitations

- Hotspot detections are **not burned area**.
- Cloud, smoke and overpass gaps cause **missing observations, not absent fires**.
- Thermal sensors also see gas flares, volcanoes and industry, so some areas show a
  permanent false fire season.
- Factors fitted on few overlap years are weak, and the interface says so per value.

## Running it

```bash
pip install duckdb numpy
python3 -m pipeline.build --raw data/raw --out site/data \
    --area punjab --area portugal --area highlands
cd site && python3 -m http.server 8000
```

Put FIRMS CSV exports in `data/raw/`. Any file whose name contains `modis` or `viirs` is
picked up. Archive extracts come from the
[FIRMS archive download](https://firms.modaps.eosdis.nasa.gov/download/); recent days come
from the [area API](https://firms.modaps.eosdis.nasa.gov/api/area/), which needs a free
MAP_KEY and serves one to five days per request.

Without real data, `python3 pipeline/synth.py data/raw` writes a synthetic FIRMS-shaped
dataset that reproduces the three properties harmonisation has to deal with. It is for
development only, and the interface shows a banner whenever the site is built from it.

`node tools/smoke.mjs` executes the page's own JavaScript against the generated JSON and
fails on runtime errors, empty renders, out-of-range percentiles or `undefined` in the
output.

## Layout

```
pipeline/schema.py      both sensors into one table
pipeline/grid.py        gridding, cell-days, area rollups
pipeline/calibrate.py   FRP floor, overlap ratios, harmonised series
pipeline/stats.py       climatology, percentile anomalies, seasonal Mann-Kendall, seam test
pipeline/current.py     like-for-like month-to-date comparison
pipeline/build.py       orchestrator, writes the site JSON
pipeline/synth.py       synthetic FIRMS data for development
site/index.html         the whole front end, no build step
tools/smoke.mjs         front-end smoke test
```

The front end is static and self-contained on purpose: everything is precomputed, so there
is no backend to fall over.

Colour ramp is **cividis**, which is perceptually uniform and stays readable with colour
vision deficiency. Anomaly states are never encoded as red against green.

## Data

NASA FIRMS, MODIS Collection 6.1 and VIIRS 375 m (S-NPP, NOAA-20, NOAA-21).
